01 제네릭과 분산(variance)

기초에서 List<String> 정도로 썼다면, 여기서는 제네릭 클래스/함수를 직접 만들 때 필요한 in/out 분산과 reified를 다룹니다.

// 제네릭 클래스
class Box<T>(var value: T)

val intBox = Box(1)
val strBox = Box("hi")

// 제네릭 함수
fun <T> firstOrNull(list: List<T>): T? = if (list.isEmpty()) null else list[0]

out — 공변(covariant), 생산자

// List<out T>는 T를 "내보내기만" 함 (읽기 전용이라 안전)
interface Producer<out T> {
    fun produce(): T
}

val strings: Producer<String> = object : Producer<String> {
    override fun produce() = "hello"
}
val anyProducer: Producer<Any> = strings   // OK — String은 Any의 하위 타입이므로 허용

in — 반공변(contravariant), 소비자

interface Consumer<in T> {
    fun consume(item: T)
}

val anyConsumer: Consumer<Any> = object : Consumer<Any> {
    override fun consume(item: Any) { println(item) }
}
val stringConsumer: Consumer<String> = anyConsumer   // OK — Any를 처리할 수 있으면 String도 처리 가능
기억하는 법 out은 반환 타입 자리에만 등장(생산), in은 파라미터 자리에만 등장(소비). List는 out, Comparator는 in이 붙는 이유가 여기서 나옵니다.

reified — 런타임에도 타입 정보 유지

일반 제네릭은 JVM의 타입 소거(type erasure) 때문에 런타임에 T가 뭔지 알 수 없습니다. inline + reified를 쓰면 예외적으로 가능합니다.

inline fun <reified T> Any?.isInstanceOf(): Boolean = this is T

"hello".isInstanceOf<String>()   // true
42.isInstanceOf<String>()         // false

// 실무 예: JSON 역직렬화 헬퍼
inline fun <reified T> parseJson(json: String): T =
    Gson().fromJson(json, T::class.java)   // T::class 를 런타임에 그대로 사용 가능

02 위임 (by)

상속 대신 "위임"으로 재사용하는 Kotlin 1급 문법입니다. 클래스 위임과 프로퍼티 위임 두 종류가 있습니다.

클래스 위임

interface Repository {
    fun findById(id: Int): String?
}

class InMemoryRepository : Repository {
    private val data = mutableMapOf(1 to "Kim")
    override fun findById(id: Int) = data[id]
}

// LoggingRepository는 Repository의 모든 메서드를 base에 위임하면서
// 필요한 것만 오버라이드
class LoggingRepository(private val base: Repository) : Repository by base {
    override fun findById(id: Int): String? {
        println("조회: $id")
        return base.findById(id)
    }
}

프로퍼티 위임 — lazy

val expensive: String by lazy {
    println("최초 접근 시 한 번만 계산됨")
    computeExpensiveValue()
}
// expensive를 처음 읽을 때 블록이 실행되고, 이후엔 캐시된 값을 반환

프로퍼티 위임 — observable

import kotlin.properties.Delegates

class Person {
    var connected: Boolean by Delegates.observable(false) { _, old, new ->
        println("connected: $old -> $new")
    }
}

val p = Person()
p.connected = true   // 출력: connected: false -> true

직접 ReadWriteProperty를 구현해서 커스텀 위임도 만들 수 있습니다 — 예를 들어 세션 캐시, 스레드 안전한 프로퍼티 등에 활용됩니다.

03 인라인 함수

고차함수(람다를 인자로 받는 함수)는 매 호출마다 함수 객체가 생성되는 비용이 있습니다. inline은 컴파일 시점에 함수 본문을 호출부에 그대로 복사해 넣어 이 비용을 없앱니다.

inline fun measureTime(block: () -> Unit): Long {
    val start = System.currentTimeMillis()
    block()
    return System.currentTimeMillis() - start
}

val elapsed = measureTime {
    Thread.sleep(100)
}
키워드의미
inline함수 본문 + 람다를 호출부에 인라인 전개
noinline여러 람다 파라미터 중 특정 람다만 인라인 제외 (다른 함수에 넘길 때 필요)
crossinline람다를 인라인은 하되, 비지역 반환(non-local return)은 금지 (다른 실행 컨텍스트에 넘길 때)
 
inline fun runBoth(crossinline a: () -> Unit, noinline b: () -> Unit) {
    val runnable = Runnable { a() }   // crossinline이라 안전 — 여기서 return 못 함
    val stored: () -> Unit = b        // noinline이라 변수에 저장 가능
    runnable.run()
    stored()
}
실무 팁 filter, map, let, apply 같은 표준 라이브러리 함수는 전부 inline입니다. 그래서 람다를 아무리 많이 체이닝해도 함수 객체 생성 오버헤드가 없습니다.

04 연산자 오버로딩 · infix 함수

정해진 이름의 함수를 operator로 선언하면 +, [] 같은 연산자로 쓸 수 있습니다.

data class Vector2(val x: Int, val y: Int) {
    operator fun plus(other: Vector2) = Vector2(x + other.x, y + other.y)
    operator fun get(index: Int) = if (index == 0) x else y
    operator fun contains(value: Int) = value == x || value == y
}

val v = Vector2(1, 2) + Vector2(3, 4)   // Vector2(4, 6) — plus() 호출
v[0]                                      // 4 — get() 호출
2 in v                                    // true — contains() 호출

infix 함수

파라미터 하나짜리 멤버/확장 함수를 점(.)과 괄호 없이 중위 표기로 쓸 수 있게 합니다. to, and, step이 대표적입니다.

infix fun Person.assignTo(room: String): String = "${this.name} -> $room"

val result = person assignTo "101호"   // person.assignTo("101호")와 동일

05 object · companion object

object는 클래스 선언과 동시에 인스턴스를 하나만 만드는 문법입니다(싱글톤).

object SessionRegistry {
    private val sessions = mutableMapOf<Int, String>()
    fun register(id: Int, name: String) { sessions[id] = name }
    fun all() = sessions.toMap()
}

SessionRegistry.register(1, "Kim")   // 인스턴스화 없이 바로 사용

companion object — 클래스에 딸린 정적 멤버

class Person private constructor(val name: String) {
    companion object {
        const val DEFAULT_ROLE = "guest"

        fun fromRawName(raw: String): Person = Person(raw.trim())
    }
}

val p = Person.fromRawName(" Kim ")   // Java의 static factory method와 동일한 용도
Person.DEFAULT_ROLE

생성자를 private으로 막고 companion object의 팩토리 함수로만 생성을 허용하는 패턴은 검증/캐싱이 필요한 객체 생성에 자주 쓰입니다.

06 value class · sealed interface

value class (구 inline class) — 런타임 오버헤드 없는 타입 래퍼

@JvmInline
value class SessionId(val raw: Int)

fun connect(id: SessionId) { /* ... */ }

connect(SessionId(42))
// connect(42)              // 컴파일 에러 — Int와 SessionId는 다른 타입 (타입 안전성 확보)

컴파일된 바이트코드에서는 SessionId가 사라지고 그냥 Int로 취급됩니다 — 박싱 없이 타입 안전성만 얻는 트릭입니다. Int나 String 같은 원시값을 의미 단위로 구분하고 싶을 때(예: UserId vs OrderId) 유용합니다.

sealed interface — sealed class보다 유연한 계층

sealed interface UiState
data class Loaded(val items: List<String>) : UiState
data object Loading : UiState
data class Error(val message: String) : UiState

fun render(state: UiState) = when (state) {
    is Loaded -> println(state.items)
    is Loading -> println("로딩 중")
    is Error -> println("에러: ${state.message}")
    // else 불필요 — 컴파일러가 모든 하위 타입을 알고 있어 exhaustive 체크
}

data class Point(val x: Int, val y: Int)

val (x, y) = Point(1, 2)     // data class는 componentN()이 자동 생성돼서 구조분해 가능
println("$x, $y")

for ((key, value) in mapOf("a" to 1, "b" to 2)) {

}

typealias OnConnect = (Person) -> Unit

08 Sequence — 지연 평가

List의 filter/map 체이닝은 매 단계마다 새 리스트를 만듭니다(즉시 평가). Sequence는 최종 연산 시점까지 계산을 미루는 지연 평가(lazy evaluation) 컬렉션입니다.

val result = (1..1_000_000)
    .asSequence()
    .filter { it % 2 == 0 }
    .map { it * it }
    .take(3)
    .toList()   // 여기서 비로소 실제 계산 시작 — 중간 리스트를 만들지 않음

// List로 그냥 체이닝했다면 100만 개 전부에 filter/map을 적용한 뒤 앞 3개만 취함
// Sequence는 앞 3개를 채울 때까지만 원소를 처리하고 멈춤

큰 컬렉션을 여러 단계로 가공할 때, 특히 중간에 take/first처럼 일부만 필요한 경우 성능 차이가 큽니다.

09 코루틴 기초

서버/네트워크 코드에서 가장 많이 쓰게 될 부분입니다. 스레드를 블로킹하지 않고 비동기 작업을 "동기 코드처럼" 작성하게 해줍니다. kotlinx-coroutines-core 의존성이 필요합니다.

// app/build.gradle.kts에 추가
dependencies {
    implementation("org.jetbrains.kotlinx:kotlinx-coroutines-core:1.9.0")
}
import kotlinx.coroutines.*

suspend fun fetchUser(id: Int): String {
    delay(100)              // Thread.sleep과 달리 스레드를 블로킹하지 않음
    return "User($id)"
}

fun main() = runBlocking {
    val user = fetchUser(1)   // 마치 동기 함수처럼 호출
    println(user)

    launch {                   // 새 코루틴 실행 — 결과를 기다리지 않고 다음 줄로 진행
        delay(200)
        println("launch 완료")
    }

    val deferred = async {     // 값을 반환하는 코루틴
        fetchUser(2)
    }
    println(deferred.await())  // 결과가 필요한 시점에 대기
}
키워드의미
suspend이 함수는 중단(suspend)될 수 있음을 표시 — 다른 suspend 함수나 코루틴 안에서만 호출 가능
runBlocking현재 스레드를 블로킹하며 코루틴 실행 — 주로 main()이나 테스트 진입점에만 사용
launch결과값이 필요 없는 코루틴 시작 (fire-and-forget), Job 반환
async결과값이 필요한 코루틴 시작, Deferred<T> 반환 → .await()로 값 획득
흔한 실수 runBlocking을 서버의 요청 처리 경로 안에 남발하면 스레드 블로킹이 그대로 발생해서 코루틴 도입 효과가 없어집니다. runBlocking은 "동기 세계에서 코루틴 세계로 진입하는 다리" 용도로만, 최상위(진입점)에서만 쓰세요.

10 구조적 동시성

코루틴은 부모-자식 관계로 묶여서, 부모가 취소되면 자식도 함께 취소되고 부모는 모든 자식이 끝날 때까지 기다립니다. "떠다니는" 백그라운드 작업이 생기지 않도록 하는 설계입니다.

suspend fun loadDashboard() = coroutineScope {
    val users = async { fetchUsers() }
    val sessions = async { fetchSessions() }
    // 두 작업 다 끝나야 이 함수가 반환됨. 하나가 실패하면 나머지도 자동 취소됨
    Dashboard(users.await(), sessions.await())
}

// 취소 전파 예시
val job = CoroutineScope(Dispatchers.Default).launch {
    val child = launch {
        delay(1000)
        println("이 줄은 실행 안 됨")
    }
}
job.cancel()   // child도 함께 취소됨

Dispatcher — 어느 스레드(풀)에서 실행할지

launch(Dispatchers.IO) { /* 네트워크/파일 I/O */ }
launch(Dispatchers.Default) { /* CPU 연산 */ }
launch(Dispatchers.Main) { /* UI 스레드 (Android 등) */ }

withContext(Dispatchers.IO) {
    // 이 블록만 IO 디스패처에서 실행, 끝나면 원래 컨텍스트로 복귀
}

11 Flow — 비동기 스트림

단일 값을 반환하는 suspend 함수와 달리, Flow는 여러 값을 시간에 걸쳐 순차적으로 방출하는 콜드 스트림입니다. RxJava의 Observable과 비슷한 역할을 코루틴 방식으로 제공합니다.

import kotlinx.coroutines.flow.*

fun sessionUpdates(): Flow<String> = flow {
    repeat(3) { i ->
        delay(100)
        emit("update-$i")   // 값을 하나씩 방출
    }
}

fun main() = runBlocking {
    sessionUpdates()
        .filter { it.endsWith("1") || it.endsWith("2") }
        .map { it.uppercase() }
        .collect { println(it) }   // 최종 연산 — 여기서 실제로 실행됨
}
콜드 스트림 collect를 호출하기 전까지 flow { } 블록은 실행되지 않습니다. collect할 때마다 처음부터 다시 실행됩니다 — List가 아니라 "값을 만드는 레시피"에 가깝습니다.

12 DSL 만들기 (수신 객체 람다)

지금 프로젝트의 build.gradle.kts 자체가 Kotlin DSL의 예시입니다. 이런 dependencies { ... } 스타일 문법을 직접 만들 수 있습니다. 핵심은 "수신 객체를 가진 람다(lambda with receiver)"입니다.

class PersonBuilder {
    var name: String = ""
    var connected: Boolean = false
    private val roles = mutableListOf<String>()

    fun role(name: String) { roles.add(name) }

    fun build() = Person(name, connected, roles.toList())
}

// 수신 객체 람다: PersonBuilder.() -> Unit
fun person(block: PersonBuilder.() -> Unit): Person {
    val builder = PersonBuilder()
    builder.block()       // 람다 안에서 this가 builder를 가리킴
    return builder.build()
}

// 사용하는 쪽 — build.gradle.kts와 같은 느낌
val p = person {
    name = "Kim"           // this.name — builder의 프로퍼티에 바로 접근
    connected = true
    role("admin")
    role("operator")
}

PersonBuilder.() -> Unit 타입이 핵심입니다. 일반 람다 () -> Unit과 달리, 이 람다 안에서는 this가 PersonBuilder 인스턴스가 되어 마치 그 클래스 내부에 있는 것처럼 프로퍼티/함수에 바로 접근할 수 있습니다. Gradle, Ktor 라우팅, Jetpack Compose가 전부 이 패턴 위에 만들어져 있습니다.
